## 1. 실제 SNOMED CT SCTID 22종 → 147종

### 방법
`scripts/lookup_snomed_sctids.py` 가 항원 148종을 **tx.fhir.org**(SNOMED CT International)의
`ValueSet/$expand`(물질·유기체 계층 검색)와 `CodeSystem/$lookup`(존재·활성 확인)으로 조회한다.
`scripts/refine_snomed_sctids.py` 가 카테고리 규칙으로 정교화한다.

1차 자동 매칭에서 드러난 오류와 교정:

| 문제 | 예 | 교정 |
|---|---|---|
| 꽃가루 항원이 **식물** 개념에 매칭 | `Mugwort` → 식물 `Mugwort`(256340003) | 카테고리가 pollen 이면 `"<이름> pollen"` 으로 재조회하고 `pollen` 이 들어간 개념만 채택 → `Mugwort pollen`(256293000). `Oak`·`Willow`·`Birch` 등 동일 교정 |
| **성분** 코드가 항원으로 매칭 | `Hazelnut` → `Cor a 8`(446073008, nsLTP 성분) | `^[A-Z][a-z]{2} [a-z] \d+` 패턴을 배제 → `Hazelnut`(256353000) |
| 검사·항체 개념이 매칭 | `Alternaria` → `Alternaria serine proteinase` | `immunoglobulin/antibody/proteinase/…` 포함 후보 배제 → `Alternaria alternata`(36703000) |
| 동물이 **동물 자체** 개념에 매칭 | `Chicken`(닭, animal) → `Chicken - meat` | animal 카테고리는 `dander/epithelium/feathers` 개념 우선 → `Chicken feathers`(260165000) |
| 음식이 **요리·주스** 개념에 매칭 | `Grape` → `Grape juice` | 수동 확정 후 `$lookup` 재검증 → `Grapes`(256317002) |

수동 확정 17건은 모두 `$lookup` 으로 존재·활성을 다시 확인했다. 처음 추측한 값 중
`Hornbeam`(256271005 는 실제로 Willow pollen), `Salmon`, `Potato`, `Pepper` 등 **9건이 틀려서 폐기**하고
실제 검색 결과로 대체했다.

### 결과
- **147/148 항원**이 실제 SCTID 로 해석된다(별칭·수식어 포함, `Birch pollen` → `Birch` 흡수).
- 폴백은 **음성 대조 1종**뿐이다: `data/snomed_ct_unmapped.json`.

### 혼합 항원을 어떻게 처리했나
혼합 항원(`Tree mixture 1·2`, `Indoor/Outdoor mold mixture`)은 **구성 종을 성분 단위로 분해할 수 없다**.
어떤 수목·곰팡이가 섞였는지는 검사 패널 인서트에만 있고 레지스트리에는 없기 때문이다. 실제로 혼합 1과
혼합 2가 같은 OMOP concept 하나를 공유하고 있었다.

그래서 단일 종 대신 **더 넓지만 실재하는** SNOMED 개념을 쓴다. 덜 구체적일 뿐 틀린 코드가 아니고,
SNOMED 로 검증하는 수신 측이 거부하지 않는다.

| 항원 | 코드 | FSN |
|---|---|---|
| Tree mixture 1·2 | `782576004` | Tree pollen |
| Indoor/Outdoor mold mixture | `722071008` | Mold antigen |
| Histamine (SPT 양성 대조 시약) | `54235008` | Histamine |
| 2-spotted spider mite | `106854009` | Family Tetranychidae |

음성 대조(생리식염수)만 코드를 붙이지 않는다. `Sodium chloride solution`(373757009) 이 존재하지만,
대조 행에 물질 코드를 달면 수신 측이 검사 항원으로 오해할 수 있다.

### 부수적 교정 — OMOP 을 SNOMED 로 위장하지 않는다
기존에는 CDM(OMOP) `concept_id` 를 `system: http://snomed.info/sct` 로 내보냈다. concept_id 는 SCTID 가
아니므로 수신 측이 SNOMED 로 검증하면 실패한다. 이제 폴백은
`https://athena.ohdsi.org/search-terms/terms` 로 구분한다.

```json
{ "system": "http://snomed.info/sct", "code": "256262001", "display": "European white birch pollen" }
{ "system": "https://athena.ohdsi.org/search-terms/terms", "code": "36684363", "display": "Tree mixture 1" }
```

## 2. 곰팡이 ↔ 집먼지진드기 감별 (질문 답변)

### 왜 어려운가
둘 다 **통년성 실내 항원**이고, 둘 다 습할 때 심해진다. 기존 문진은 곰팡이에 대해
"장마철·습한 곳에서 심해지나요?" 한 문항만 물었는데, 이 질문은 **집먼지진드기 환자도 '예'라고 답한다**.
습도가 높으면 진드기 개체수도 함께 늘기 때문이다. 즉 이 단서 하나로는 두 항원을 가를 수 없다.

### 무엇을 추가했나
곰팡이에만 해당하고 진드기로는 설명되지 않는 단서를 묻는다.

| 문항 | 선택지 | 가리키는 쪽 |
|---|---|---|
| **어느 공간에서 심해지나** (`mold_space`, 다중) | 욕실·샤워실 / 지하실·창고·오래된 건물 / 누수·결로 자국 근처 / 에어컨·가습기 켤 때 | **곰팡이** |
| | 침실 잠자리(이불·매트리스) 주변 | **진드기** |
| **야외 상황** (`mold_outdoor`, 다중) | 낙엽 더미·풀 깎기 / 퇴비·흙·화분 / 비 온 직후·천둥번개 뒤 / 농장·건초 | **실외 곰팡이**(얼터나리아·클라도스포리움) |
| **침구 조치 반응** (`mite_bedding_trial`) | 좋아졌다 / 변화 없었다 / 해본 적 없다 | **진드기** |
| **제습·곰팡이 제거 반응** (`mold_dehum_trial`) | 좋아졌다 / 변화 없었다 / 해본 적 없다 | **곰팡이** |

공간 문항의 '침실' 선택지와 두 개의 조치 반응 문항은 **진드기도 함께 양성일 때만** 노출된다.
그때가 실제로 감별이 필요한 상황이기 때문이다.

### 판정 규칙 (`_classify_mold`)
1. 곰팡이 특이 단서(늘 젖은 공간 / 실외 포자 / 제습 후 호전)가 있으면 → **원인으로 확정**
2. 그런 단서가 없는데 진드기도 양성이고 '습할 때 악화'만 있으면 → **판정 보류**
   ("집먼지진드기도 습도가 높으면 함께 늘기 때문에 이 단서만으로는 구분할 수 없습니다")
   - 침구 조치로만 호전됐고 제습은 시도한 적 없으면 "진드기로 설명될 가능성이 더 크다"고 덧붙인다
3. 진드기가 없으면 기존대로 '습할 때 악화' 를 원인으로 인정
4. 명시적 부정(습한 곳 무관 / 해당 공간 없음 / 제습해도 변화 없음)이면 → **감작만**
   (진드기가 양성이면 "같은 실내 증상은 집먼지진드기로 설명됩니다" 를 붙인다)

### 실내 곰팡이 vs 실외 곰팡이
회피 방법이 정반대라 `mold_habitat()` 으로 갈라 조언한다.

| 구분 | 항원 | 조언 |
|---|---|---|
| 실외 | 얼터나리아, 클라도스포리움, 푸사리움 등 | 낙엽·잔디·퇴비 작업 회피, 비 온 뒤·늦여름~가을 창문 닫기 |
| 실내 | 아스페르길루스, 페니실리움, 뮤코르, 칸디다 등 | 습도 50% 이하, 누수·결로 수리, 에어컨·가습기 필터 청소 |

회귀 테스트 `test_mold_vs_mite_discrimination` 이 6가지 시나리오(구분 불가 보류, 실외 단서 확정,
젖은 공간 확정, 침구만 호전, 제습 후 호전, 명시적 부정)를 고정한다.

## 4. 결과 상담 챗봇

`POST /api/chat` · `services/result_chat_service.py` · 두 UI 의 **결과 상담** 탭.

### 근거 고정
답변은 **이 환자의 판정 결과·지식베이스·문진 답변**으로만 만든다. 시스템 프롬프트가 컨텍스트 밖
내용을 금지하고, 컨텍스트에 없으면 "이 결과로는 알 수 없다"고 답하게 한다.

실제 동작 확인:

| 질문 | 답변 |
|---|---|
| 침구는 얼마나 자주 세탁해야 하나요? | 지식베이스의 회피 수칙 그대로(주 1회, 55~60℃) |
| 고양이를 키워도 되나요? (검사에 고양이 없음) | "이 결과에서는 고양이에 대한 정보가 없습니다 … 담당 의사에게 문의하세요" |
| Should I stop my antihistamine? | "This result cannot tell. Please ask your treating clinician." |
| 지금 숨쉬기가 힘들어요 | LLM 을 거치지 않고 **즉시 응급 안내**(119·응급실·에피네프린) |

### 가드레일
- 진단·처방·약 용량 조절 금지
- 호흡곤란·아나필락시스 표현은 정규식으로 먼저 잡아 응급 안내를 우선(한/영/중)
- 답변마다 교육용 참고 자료임을 표시

### API 키 없이도 동작
추천 질문 5종(가장 조심할 것 / 판정 근거 / '감작만'의 의미 / 관찰 항목 / 주의 음식)은
LLM 없이 판정 데이터에서 **결정론적으로** 답한다. Df/Dp 는 임상 그룹으로 한 번만 세고,
표현만 다른 중복 수칙은 걸러낸다.

## 5. 서버 생성 콘텐츠 다국어화 (문진·지식베이스·리포트·카드뉴스)

### 왜 사전이 아닌가
화면 크롬은 문구가 고정이라 `web/i18n.js` 사전으로 충분했다. 서버 콘텐츠는 항원 148종 ×
지식베이스 필드 + 환자별로 조합되는 문장이라 사전으로 감당되지 않는다.
그래서 **LLM 번역 + 영구 캐시**를 쓴다(`services/translation_service.py`).

### 동작
| 대상 | 방식 |
|---|---|
| 문진 문항·옵션·섹션 | JSON 에서 `title/help/subtitle/label/hint` 값만 번역(식별자·코드는 불변) |
| 맞춤 리포트 | 마크다운을 빈 줄 기준 **블록 단위**로 번역 → 캐시 재사용률 높음 |
| 리포트 문서 HTML | 본문은 위에서 번역되고, 표지·타일 등 고정 문구만 HTML 번역 |
| 카드뉴스 HTML | 텍스트 노드만 번역 |
| 도감 카드 근거 | `assessments` 의 `rationale_ko`·KB 필드 번역 |

### 안전장치
- `lang=ko` 는 번역 경로를 **아예 타지 않는다**(기존 동작·테스트 불변)
- API 키가 없으면 원문(한국어)을 그대로 반환 — 조용히 비우지 않는다
- `<style>`/`<script>` 블록 제외(CSS 주석의 한국어까지 번역하면 스타일이 깨진다)
- `<b>` → `**굵게**` → `<b>` 왕복으로 문장을 조각내지 않고 강조를 보존
- `<br>` 는 자리표시자로 바꾸고, 번역문에서 유실되면 **그 문장만 원문 유지**
- 숫자·단위·학명·**환자 이름**은 번역하지 않도록 프롬프트로 고정
- 기계 번역임을 UI 배너로 명시

### 성능·비용
캐시 702건을 저장소에 동봉해 배포 직후에도 한/영/중이 즉시 동작한다.
캐시 적중 시 문진 응답 **0.0초**. 미적중(첫 중국어 전체 흐름)은 약 40초, 이후 0초.
