01. 범위와 안전 경계

이 플랫폼은 검사값과 문진을 구조화하고, 결정 규칙으로 결과를 설명하는 연구용 구현입니다.

구현된 범위

  • SPT, MAST, UniCAP 이미지 OCR
  • OCR 행별 의심 표시와 사람 검수
  • 양성 항목별 문진과 감별 상태
  • 리포트, 카드뉴스, 결과 상담 문맥
  • FHIR R4 형태의 Bundle
  • RDF 그래프와 제한된 SPARQL

보증하지 않는 범위

  • 의사의 진단과 처방
  • 환자별 위험 확률
  • OWL 추론기 기반 완전한 ontology
  • 외부 FHIR profile 적합성
  • 실제 환자 일반화와 임상 효용
  • 후보 근거의 자동 승인
상태 표기구현은 현재 코드 경로를 뜻합니다. 제안·후보는 검토가 남은 지식이나 절차입니다. 미검증은 임상 또는 외부 표준 검증이 끝나지 않은 범위입니다.
임상 경계검사 양성은 감작을 뜻합니다. 약물 항원은 시스템이 확정하지 않으며, clinician_review로 분리합니다.

코드 근거: models/schemas.py · ClinicalRelevance, ontology_service.py · 사용 제약

04. Ontology 구현

현재 구현은 JSON 스냅샷을 런타임 RDF 그래프로 변환하는 경량 지식 계층입니다.

RDF와 OWL의 경계현재 코드는 RDF triple을 만들고 검색합니다. OWL axiom, reasoner, entailment, consistency 검사는 구현하지 않습니다. 따라서 추론 완료 ontology로 보고하면 안 됩니다.
입력 구조RDF 타입/관계보존 메타데이터
topicTopic, query, aliaslabel, source URL
clinical_context.itemsExpressionGroup, hasExpressionpredicate, polarity, reviewStatus
recordsClaim, claimclaim ID, evidence ID, raw text
terminology_summaryOntologyTerm, mappedTo, subClassOfsystem, code, release, synonym
source_evidenceEvidencetext, URL, revision, sheet

Namespace는 https://apaaaci.local/allergy-ontology#입니다. rdflib.Graph는 최초 접근 때 생성됩니다.

스냅샷은 5개 질환 주제를 담습니다. 이 안에는 161개 expression group과 1,130개 evidence cell이 있습니다. 모든 임상 주장은 candidate이며 accepted는 0개입니다.

질의 경계

SPARQL API는 SELECT와 ASK만 허용합니다. 업데이트, SERVICE, 데이터 이동 명령은 차단합니다.

실제 서버에서 검증한 SPARQL
PREFIX allergy: <https://apaaaci.local/allergy-ontology#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT ?group ?label ?predicate ?status ?evidence
WHERE {
  ?group a allergy:ExpressionGroup ;
         rdfs:label ?label ;
         allergy:predicate ?predicate ;
         allergy:reviewStatus ?status ;
         allergy:evidenceCount ?evidence .
  FILTER(?predicate = "evaluated_with")
}
ORDER BY DESC(?evidence)
LIMIT 3

2026-10-29에 POST /api/ontology/sparql로 실행했습니다. 서버는 다음 첫 행을 반환했습니다.

{
  "group": "https://apaaaci.local/allergy-ontology#clinical-expression-group:37b8270e86dacc70a4cced1a",
  "label": "based on symptoms",
  "predicate": "evaluated_with",
  "status": "candidate",
  "evidence": "2"
}

rdfs prefix는 rdflib 기본 환경에 기대지 않고 명시합니다. allergy:predicate와 allergy:evidenceCount는 그래프 구축 코드가 실제로 생성합니다.

환경관리 JSON은 같은 그래프에 선택적으로 추가됩니다. 이 계층의 내부 상태는 textbook_curated입니다. 파일은 전문의 검토 전이라고 따로 밝힙니다.

코드 근거: 경로와 namespace, 상태와 SPARQL 제한, 지연 적재, RDF 변환. 표준: W3C RDF 1.1

05. Evidence, provenance, 검토 상태

근거를 사용할 때는 주장, 원문 셀, 판본, 검토 상태를 한 묶음으로 추적합니다.

저장 검사값 기반 연구 자료별도 카탈로그는 실제 저장 검사값으로 만든 87세트를 제공합니다. 이 자료는 아래 합성 예시와 다릅니다. 현재 로컬 템플릿을 사용했으며, screening=None과 answers={}를 적용했습니다. 문진은 실행하지 않았습니다. 이름과 검사일은 제거했습니다. 생성 조건과 Evidence 다운로드를 확인하십시오.
근거 층출처상태 의미허용 용도

provenance 필수 묶음

  • claim_id: 구조화된 주장 ID
  • evidence_id: 원문 셀 또는 출처 ID
  • source_url 또는 서지 인용
  • review_status: 후보와 검토 상태
  • quote/raw_text: 문맥 확인용 원문

금지되는 해석

  • polarity=positive를 임상 효과로 읽지 않습니다.
  • 근거 셀 수를 근거 수준 점수로 쓰지 않습니다.
  • textbook_curated를 전문의 승인으로 읽지 않습니다.
  • 일반 지식을 환자별 원인 판정에 쓰지 않습니다.

06. OCR, 파싱, 사람 검수

OCR은 값을 읽고 규칙 검사를 붙입니다. 시스템은 의심값을 임의로 정답으로 고치지 않습니다.

비식별 합성 OCRResult
{
  "test_type": "UniCAP",
  "patient": {"name": "SYNTHETIC-001", "test_date": "2026-01-15"},
  "results": [{
    "index": 1,
    "raw_text": "d1 D. pteronyssinus 2.10 class 2",
    "allergen_name": "D. pteronyssinus",
    "value": 2.1,
    "value_raw": "2.10",
    "unit": "kU/L",
    "class": 2,
    "interpretation": "Positive",
    "review_flags": []
  }]
}

보존 규칙

  • <0.35는 value_text로 보존합니다.
  • .48 같은 인쇄 문자열은 value_raw에 남깁니다.
  • 인쇄 문자열과 모델 숫자가 다르면 충돌을 표시합니다.
  • SPT 장축, 단축, 평균, A/H 비를 구분합니다.
  • Total IgE 같은 요약 행은 알레르겐에서 제외합니다.

곰팡이곰팡이 특이 공간·실외 포자·제습 후 호전특이 단서가 있으면 최우선. 진드기 음성일 때 습기나 계절 겹침도 사용명시적 no, 제습 후 변화 없음, 계절 불일치진드기도 양성이고 습기만 yes이면 원인 구분 보류

갑각류전신 음식 게이트 → 항목별 섭취 반응전신 또는 입·목 증상실제 섭취해도 증상 없음먹지 않았거나 정보 부족
일반 음식전신 음식 게이트 → 증상 다중 선택피부·소화기·호흡기·아나필락시스, 또는 입·목 증상none만 선택하고 전신 음식으로 지목되지 않음섭취 경험 또는 증상 답이 부족
약물다른 분기보다 항상 우선앱은 이 상태를 만들지 않음앱은 이 상태를 만들지 않음반응 유무와 무관하게 clinician_review
꽃가루 판정의 정확한 순서
  1. 항원 category로 tree, grass, weed 질문군을 고릅니다.
  2. 항원별 peak month와 환자 worse month의 교집합을 계산합니다.
  3. 해당 시기 직접 질문이 yes면 월 계산보다 먼저 실제 주의로 둡니다.
  4. 직접 질문이 no면 월 계산보다 먼저 감작만으로 둡니다.
  5. 직접 답이 없을 때만 월 교집합을 사용합니다.
  6. 두 입력이 모두 없으면 관찰 필요로 둡니다.

OAS 음식은 rationale을 보강합니다. OAS 자체가 꽃가루 verdict를 덮어쓰지는 않습니다.

진드기와 곰팡이를 함께 해석하는 순서
  1. 곰팡이 전용 공간, 실외 포자, 제습 반응을 먼저 찾습니다.
  2. 전용 단서가 있으면 곰팡이를 실제 주의로 분류합니다.
  3. 전용 단서가 없고 진드기도 양성이면 습기 하나만으로 곰팡이를 확정하지 않습니다.
  4. 침구 관리만 효과가 있고 제습을 시험하지 않았다면 진드기 설명 가능성을 rationale에 남깁니다.
  5. 명시적 무관 답이나 계절 불일치가 있으면 감작만으로 둡니다.
음식과 약물의 안전 분기

음식은 실제 섭취 반응을 봅니다. 전신 반응 선택은 항목별 답보다 강한 게이트입니다. 입·목 증상도 실제 주의에 포함되지만 symptom site는 전신 부위와 분리합니다.

약물은 모든 경우에 의료진 검토로 둡니다. 반응, 문제없는 사용, 미사용 정보는 삭제하지 않습니다. 이 정보는 rationale, reported symptoms, severity에 보존합니다.

답변 정규화

서버는 화면의 답을 question spec으로 제한합니다. 배타값, 허용 옵션, 숨겨진 질문을 확인한 뒤 분류에 사용합니다.

답변 정규화가 필요한 이유

  • 문진에 없는 question ID는 ignored_answers로 보냅니다.
  • 선택지에 없는 값은 판정에 사용하지 않습니다.
  • none 같은 배타값은 다른 선택과 함께 유지하지 않습니다.
  • 현재 화면에서 숨겨진 후속 질문은 판정 근거로 사용하지 않습니다.
  • 판정, 상담, FHIR는 같은 정리된 답을 다시 사용합니다.
재현성LLM은 판정 핵심 경로에 필요하지 않습니다. 같은 입력과 코드면 같은 상태가 나옵니다.
분류와 진단clinically_relevant는 문진 규칙의 출력입니다. 진료에서 확정한 진단과 같다고 단정하지 마십시오.

코드 근거: 상태 정의, assessment, 답 정규화, 분류

08. 리포트와 카드뉴스

현재 환자 리포트와 카드뉴스는 판정 객체와 지식베이스에서 결정론적으로 구성됩니다.

실제 저장값 출력과 합성 예시를 구분하십시오.별도 카탈로그의 리포트와 카드뉴스는 실제 저장 검사값으로 만들었습니다. 현재 로컬 템플릿을 사용했지만, 이 절의 합성 예시와는 별도 자료입니다. screening=None과 answers={}를 적용했으므로 문진 기반 판정을 포함하지 않습니다. 생성 조건과 다운로드 형식을 확인하십시오.

리포트

  • 한눈에 보기와 상태별 개수
  • 실제 주의 항원 우선순위
  • 약물 항원의 별도 진료 확인
  • 확인된 음식 교차반응 경고
  • 환경관리 근거와 검토 전 고지
  • Markdown, HTML 문서, PDF

카드뉴스

  • 표지와 상태별 요약 카드
  • 예방, 노출, 계절, 치료 카드
  • 항원별 상세 카드
  • 결과에 맞춘 quiz 카드
  • 내장 CSS/JavaScript HTML deck
  • quest와 classic 디자인 변형

생성 경계

한국어 경로는 결정론적 문장 조립을 사용합니다. 다른 언어는 블록 번역과 캐시를 사용할 수 있습니다. 과거 generate_report()에는 LLM 경로가 남아 있습니다. 연구자는 호출한 함수 이름을 기록해야 합니다.

리포트 선택 규칙

  • 표의 개수는 검사 행 수가 아니라 접힌 임상 그룹 수입니다.
  • 실제 주의, 감작만, 관찰 필요, 약물 검토를 서로 다른 목록으로 만듭니다.
  • 검사 음성과 경계 항목은 tested negatives에서 별도로 가져옵니다.
  • 확인된 OAS·교차반응 음식은 음식 중심 경고로 올립니다.
  • 환경 근거는 관련 항원만 선택하고 검토 상태를 표시합니다.
  • 주증상, 계절, 지역, 치료 사용 여부가 해당 절을 조건부로 엽니다.

09. 결과 상담

상담은 환자 결과 문맥과 제한된 일반 지식을 사용하며, 진단과 처방을 금지합니다.

문맥 구성

  • 검사 종류와 환자 기본 정보
  • 상태별 항원과 감별 근거
  • 검사 음성·경계 항목
  • 스크리닝과 문진 답변
  • 질문이 요구할 때만 ontology 근거
  • 환경관리와 care guidance

지식 주입 조건

기저질환을 골랐다는 이유만으로 ontology를 넣지 않습니다. 질문에 일반지식 의도가 있을 때 관련 주제를 고릅니다.

안전 동작

응급 표현은 LLM 이전에 확인합니다. 결과 범위 밖 질문에는 알 수 없다고 답하도록 프롬프트를 구성합니다. 치료 정보는 일반 정보로 제한합니다.

평가 항목근거성과 근거 ID 일치를 각각 측정하십시오. 범위 밖 질문 거절, 응급 분기, 처방 금지, 다국어 의미 보존도 측정하십시오.

코드 근거: build_context, ontology_block, system prompt, answer

10. FHIR 변환

검사 측정은 Observation으로, 감별 결과는 AllergyIntolerance로 분리합니다.

저장 검사값 기반 FHIR별도 카탈로그의 FHIR는 실제 저장 검사값과 현재 로컬 템플릿으로 만들었습니다. 이 절의 합성 예시와 다릅니다. screening=None과 answers={}를 적용했으므로 AllergyIntolerance의 검증 상태는 unconfirmed입니다. 생성 조건과 FHIR 다운로드를 확인하십시오.
자원 의미Observation은 검사에서 관찰한 값입니다. AllergyIntolerance는 물질 반응 위험에 대한 임상 평가입니다. 양성 Observation만으로 AllergyIntolerance를 확정하지 않습니다.

done=true는 성공을 뜻하지 않습니다. pending과 running이 더 없다는 뜻입니다. failed, skipped, missing도 done에 포함될 수 있습니다.

  • rate limit은 프로세스 메모리에 있습니다.
  • API 응답은 기본 no-store입니다.
  • 세션 ID는 결과 열람 권한입니다.

LLM routing과 예산

  1. X-LLM-Backend가 유효하고 사용 가능하면 요청 backend로 씁니다.
  2. 그렇지 않으면 LLM_BACKEND를 봅니다.
  3. OpenAI는 번호 키가 하나라도 있으면 단일 키를 쓰지 않습니다.
  4. 번호 키는 요청마다 round-robin으로 선택합니다.
  5. 예산 모델 누적 total token이 임계값 미만이면 예산 모델을 씁니다.
  6. 임계값 이상이면 vision 또는 chat 기본 모델로 전환합니다.
  7. 성공한 OpenAI 호출만 장부에 기록합니다.

장부 잠금은 한 프로세스 안에서만 안전합니다. 여러 worker가 같은 JSON을 쓰면 집계가 어긋날 수 있습니다. 휘발 디스크는 배포마다 사용량을 잃습니다.

번역 상태와 보호 범위

  • ko 요청은 번역하지 않습니다.
  • 환자 이름, 기관, 날짜, 자유 기재를 placeholder로 가립니다.
  • 식별값은 일반 번역 캐시에 넣지 않습니다.
  • 자유 기재 번역은 영구 cache에 넣지 않습니다.
  • 번역 segment가 하나라도 남으면 ready로 저장하지 않습니다.
  • 원 요청 언어 실패가 classify 자체를 실패시키지는 않을 수 있습니다.

  7. 해당 서비스의 단위 테스트와 snapshot을 추가합니다.
  8. 관련 리포트, 카드뉴스, 상담, FHIR 영향을 확인합니다.
  9. 독립 검토자가 근거와 문구를 판정합니다.
  10. 승인 결과, 코드 commit, 데이터 hash를 release record에 고정합니다.

연구자 질문 6개

1. 검사 양성이면 AllergyIntolerance를 confirmed로 보내도 됩니까?

안 됩니다. 검사 양성은 Observation에 보존합니다. 문진 규칙이 노출과 증상 연결을 확인한 경우만 현재 구현이 confirmed를 사용합니다. 이 상태도 임상 확정 진단을 보증하지 않습니다.

2. ontology의 candidate claim을 환자 판정 근거로 써도 됩니까?

안 됩니다. candidate claim은 질환 일반 설명 후보입니다. 환자별 수치의 근거는 검사 결과입니다. 환자별 관련성의 근거는 screening과 문진 답입니다.

3. /api/classify 한 번으로 모든 산출물이 생깁니까?

리포트와 카드뉴스는 생깁니다. FHIR는 포함되지 않습니다. 같은 ClassifyRequest를 /api/fhir에 별도로 보내십시오. PDF도 저장 세션의 ready 언어에서 별도 요청합니다.

4. done=true이면 세 언어가 모두 성공했습니까?

아닙니다. done은 pending과 running이 없다는 뜻입니다. failed, skipped, missing이 남아도 true일 수 있습니다. ready 목록과 각 status를 함께 확인하십시오.

5. 카드뉴스 체크와 퀴즈를 연구 outcome으로 쓸 수 있습니까?

현재 상태만으로는 어렵습니다. 체크와 진행은 브라우저 메모리 중심이며 서버 연구 event로 저장되지 않습니다. 동의, event schema, 결측 정의, 분석 계획을 먼저 설계하십시오.

6. 새 항원을 추가하면 어디까지 다시 검증해야 합니까?

이름 검색, OCR 매핑, category 질문, 판정, 리포트, 카드뉴스, 상담, FHIR coding을 확인하십시오. 지식 문구는 candidate로 시작하고 별도 검토를 거치십시오.
