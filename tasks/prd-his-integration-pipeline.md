- 관련: `tasks/tasks-prd-his-integration-pipeline.md`(작업 목록) · `docs/plan_2026-10-13_HIS연동_자동화_고도화.html`(인터랙티브 과업판) · Notion「HIS 연동 자동화 고도화」

## 1. Introduction / Overview

지금 플랫폼은 환자(또는 의료진)가 검사 결과지 **이미지를 올리면 OCR** 로 읽고, 문진 → 임상적 의미 판정 → 리포트·카드뉴스·FHIR·챗봇으로 이어진다. 이 PRD 는 그 앞뒤를 병원 시스템과 잇는다.

1. 병원에서 알레르기 검사가 시행·결과 보고되면 **HIS/LIS 가 결과를 우리 서버로 자동 전송**한다(OCR 단계 제거).
2. 동시에 환자에게 **카카오 알림톡으로 설문(문진) URL** 을 보낸다.
3. 환자가 설문을 끝내면 **리포트를 자동 생성**해 **PDF·카드뉴스·결과 상담 챗봇 URL/QR** 을 알림톡으로 전달한다.
4. 전 과정은 **병원 내 로컬 서버와 GPU** 에서 돌아간다(환자 식별정보가 원외로 나가지 않음).

문제: 현재 흐름은 환자가 결과지를 사진 찍어 올려야 시작되고, OCR 오류 점검이 필요하며, 외부 LLM API 를 쓴다. 병원 진료 흐름에 붙지 않아 실제 환자에게 닿는 비율이 낮다.

목표: **검사 결과 보고 시점부터 환자가 리포트를 받을 때까지 사람 손을 거치지 않는 파이프라인**을 병원 내부망에서 운영한다.

## 2. Goals

| # | 목표 | 측정 |
|---|---|---|
| G1 | HIS 결과 자동 수신 | 알레르기 검사 결과 건수 대비 수신·파싱 성공 ≥ 99% (파일럿 기간) |
| G2 | 환자 도달 | 알림톡 발송 성공(도달) ≥ 95%, 실패 시 SMS 대체 발송 |
| G3 | 설문 완료 | 알림톡 수신 환자의 설문 완료율 ≥ 50% (파일럿 목표, 72시간 내) |
| G4 | 리포트 자동 생성 | 설문 완료 → 리포트·PDF·카드뉴스 전달까지 p95 ≤ 10분(로컬 LLM 기준), 실패율 < 1% |
| G5 | 원외 반출 없음 | 환자 식별정보(이름·등록번호·연락처)가 병원망 밖으로 나가는 경로 0건(알림톡 발송 구간은 전화번호·토큰 URL 만) |
| G6 | 품질 유지 | 로컬 LLM 리포트 문장 품질이 현행 외부 모델 대비 전문의 평가에서 동등 이상(5점 척도 차이 ≤ 0.3) |
| G7 | 운영 가시성 | 관리자 화면에서 건별 상태(수신 → 발송 → 설문 → 생성 → 전달)와 실패 재시도를 볼 수 있음 |

## 3. User Stories

- **환자**로서, 검사 다음 날 알림톡으로 설문 링크를 받아 5~10분 안에 답하면, 내 결과를 쉬운 말로 설명한 리포트와 카드뉴스를 받고 궁금한 것을 챗봇에 물을 수 있다.
- **알레르기내과 의사**로서, 환자가 외래에 오기 전에 "실제 주의 / 감작만 / 관찰 필요" 판정과 문진 답변을 보고 진료 시간을 아낄 수 있다.
- **의료정보팀 담당자**로서, 기존 인터페이스 엔진에 결과 라우팅 한 건을 추가하고 네트워크·보안 심의를 통과시키면 그 뒤 운영은 우리 팀이 맡는다.
- **우리 팀 개발자(김형기 프로)** 로서, HIS 수신 어댑터·알림톡 클라이언트·작업 큐를 붙이되 기존 판정·리포트·FHIR 코드는 그대로 재사용한다.
- **운영자**로서, 어떤 환자가 어느 단계에서 멈췄는지 보고 재발송·재생성 버튼으로 복구할 수 있다.

## 4. Functional Requirements

### 4.1 HIS 결과 수신 (워크스트림 A)
1. 시스템은 다음 세 방식 중 의료정보팀이 정하는 하나(또는 단계적 복수)로 알레르기 검사 결과를 수신해야 한다.
   - **A-1 HL7 v2 ORU^R01 (MLLP)** — 인터페이스 엔진이 알레르기 검사(MAST·ImmunoCAP·SPT) 결과만 우리 수신기로 라우팅. OBR(검사 오더)·OBX(항원별 결과: 코드·값·단위·class·참고치)·PID(환자)·PV1(진료과) 파싱.
   - **A-2 FHIR R4** — HIS FHIR 서버의 `DiagnosticReport`/`Observation` 을 Subscription 또는 주기 pull(`_lastUpdated`)로 수신.
   - **A-3 DB 읽기 전용 뷰 또는 배치 파일(CSV/Excel)** — 인터페이스 개발 없이 야간 배치 또는 10분 주기 조회로 시작하는 저비용 안.
2. 수신 어댑터는 세 방식 모두 **내부 공통 스키마**(현행 `OCRResult`/`AllergenResult` 와 동일: 검사 종류·항원명·값·단위·class·양성 여부·검사일·검사기관)로 정규화해야 한다. 이후 단계(항원 정규화·SNOMED 매핑·판정·리포트·FHIR)는 기존 코드를 그대로 쓴다.
3. **멱등성**: 접수번호(또는 오더번호+검사코드)를 키로 중복 수신을 무시하고, 결과 수정(corrected result) 메시지는 새 버전으로 기록해야 한다.
4. 항원 코드 매핑: HIS/LIS 검사코드 ↔ 내부 항원 레지스트리(`data/allergens.json`, SNOMED 147종) 매핑표를 의료정보팀이 제공하는 검사 마스터로부터 만들고, 미매핑 코드는 관리자 화면에 큐잉해야 한다.
5. 수신 시 ACK(AA/AE/AR) 를 올바르게 반환하고, 파싱 실패 메시지는 원문을 보관하고 알림을 보내야 한다.
6. **대상 필터**: 파일럿 기간에는 알레르기내과 오더, 검사 종류 MAST·ImmunoCAP 만 처리하고 그 외는 기록만 한다(설정으로 확장).
7. OCR 업로드 경로는 유지한다(타 기관 결과지·과거 결과용). HIS 수신 건은 OCR·결과 점검 화면을 건너뛴다.

### 4.2 환자 식별·동의·토큰 (워크스트림 B)
8. 환자 식별자(등록번호)는 서버 내부에서만 쓰고, 외부로 나가는 URL 에는 **일회성 불투명 토큰**(예: 32바이트 난수, 만료 14일, 1회 본인확인 후 세션 쿠키) 만 넣어야 한다.
9. 설문 첫 화면에서 **간단한 본인확인**(생년월일 6자리 또는 전화번호 뒤 4자리) 을 요구하고, 5회 실패 시 토큰을 잠가야 한다.
10. 발송 전 **동의 확인**: HIS 의 문자/알림톡 수신 동의 플래그를 조회하거나, 검사 접수 시 안내문에 서비스 동의를 포함하는 절차를 의료정보팀·진료과와 정해야 한다(IRB/개인정보 영향평가 결과에 따름).
11. 세션 데이터 보존기간(예: 90일)과 삭제 정책을 설정으로 두고, 만료 세션의 PDF·대화 기록은 자동 삭제해야 한다.
12. 모든 접근(발송·열람·다운로드·챗)은 감사 로그(누가·언제·어떤 세션·어떤 행위) 를 남겨야 한다.

### 4.3 알림톡 발송 (워크스트림 C)
13. 알림톡은 병원이 이미 계약한 발송 대행사 API 로 보내고, 템플릿은 카카오 심사를 통과한 문구를 써야 한다. 템플릿은 최소 3종: **① 설문 안내**(검사 결과 보고됨 + 설문 URL), **② 리포트 완료**(PDF·카드뉴스·챗봇 URL/QR), **③ 리마인드**(48시간 미완료 시 1회).
14. 알림톡 실패(미가입·차단) 시 **SMS/LMS 대체 발송**, 그래도 실패하면 관리자 큐에 표시해야 한다.
15. 발송 시각 정책: 08:00~20:00 사이에만 발송하고, 그 외 시간 수신 건은 다음 발송 시간대로 미룬다.
16. 발송 결과 콜백(도달·읽음·실패) 을 수신해 상태를 갱신해야 한다.
17. URL 은 병원 외부에서 접근 가능한 공개 도메인(예: `https://allergy.<병원도메인>`) 이어야 하며, 역방향 프록시(DMZ) 를 통해 내부 서버로 연결된다.

### 4.4 환자 설문 (워크스트림 D)
18. 설문은 현행 스크리닝 + 양성 항원별 감별 문진(`questionnaire_service`) 을 그대로 쓰되, **모바일 알림톡 인앱 브라우저**에서 끊김 없이 동작해야 한다(세로 화면, 큰 터치 영역, 진행 저장·재개).
19. 환자 기본정보(이름·나이·성별)는 HIS 에서 받으므로 입력받지 않고 확인만 한다.
20. 설문 중단 후 같은 토큰으로 재진입하면 이어서 할 수 있어야 하며, 완료 시 재제출은 막는다(수정은 외래에서 의료진이).
21. 설문 완료 즉시 **"리포트를 준비 중이며 완료되면 알림톡으로 보내드립니다"** 화면과, 바로 볼 수 있는 간이 결과(판정 요약) 를 보여준다.

### 4.5 리포트 생성·전달 (워크스트림 E)
22. 설문 완료 이벤트는 **작업 큐**(로컬 Redis 또는 SQLite 기반 큐) 에 넣고 워커가 판정 → 리포트(MD/HTML) → PDF → 카드뉴스 → FHIR 번들 → 알림톡 ② 순으로 처리해야 한다. 실패 단계부터 재시도(지수 백오프 3회) 가 가능해야 한다.
23. LLM 호출(리포트 문장·번역·챗봇) 은 **병원 내 Ollama** 로 가고, 외부 API 호출 경로는 설정으로 **완전히 차단**할 수 있어야 한다(`LLM_BACKEND=ollama`, 외부 키 미설정 시 기능 저하 없이 결정론 경로로 동작).
24. PDF·카드뉴스는 토큰 URL 로 다운로드(만료 14일, 다운로드 횟수 기록) 하고, 알림톡에는 링크와 **챗봇 QR 이미지** 를 첨부한다.
25. 챗봇은 현행 `/api/sessions/{id}/chat` 을 토큰 인증으로 열고, 응급 표현 가로채기·진단/처방 금지 규칙을 유지한다.
26. 의료진용: 외래 진료 전 조회 화면(환자별 판정·문진 답변·리포트) 과 HIS 에 되돌려 줄 **FHIR AllergyIntolerance/Observation 번들** 또는 PDF 첨부 전송 방식을 의료정보팀과 정한다(2차 범위).

### 4.6 로컬 서버·GPU 운영 (워크스트림 F)
27. 배포는 `docker compose`(앱·워커·Ollama·역프록시·큐) 로 병원 로컬 서버에 올리고, GPU 는 Ollama 컨테이너가 쓴다.
28. 모델: 챗·리포트용 1종(예: Qwen 계열 32B 또는 gpt-oss-120b 급 — GPU 메모리에 맞춰 선택), 번역 캐시는 동봉분(965건) 재사용. OCR 비전 모델은 HIS 경로에서 불필요하나 업로드 경로용으로 선택 탑재.
29. 성능 기준: 리포트 1건 LLM 구간 ≤ 3분, 챗 1턴 ≤ 15초(p95), 동시 5세션. 미달 시 모델 축소·양자화·vLLM 전환을 평가한다.
30. 모니터링: 헬스체크, 큐 적체, GPU 사용률, 디스크, 알림톡 실패율 알림(메일 또는 사내 메신저).
31. 백업·복구: 세션 DB·PDF 저장소 일 1회 백업, 복구 절차 문서화.

### 4.7 관리자·운영 (워크스트림 G)
32. 관리자 화면(기존 `/admin` 확장): 건별 상태 타임라인, 재발송·재생성, 미매핑 검사코드 처리, 템플릿 미리보기, 일/주 통계(수신·발송·완료·생성·전달).
33. 운영 매뉴얼: 장애 유형별 대응(인터페이스 중단·알림톡 실패·GPU 다운), 담당 연락망.

### 4.8 거버넌스 (워크스트림 H)
34. IRB(연구 목적이면) 또는 QI/서비스 승인, 개인정보 영향평가, 보안 심의(망 구성·암호화·접근통제) 를 파일럿 전에 통과해야 한다.
35. 환자 안내문·동의 문구·알림톡 템플릿 문구는 진료과(알레르기 전문의) 와 개인정보 담당자가 검수한다.
36. 리포트·챗봇의 모든 의학 문장은 "진단·처방이 아님" 고지를 유지하고, 전문의 검토 상태(`candidate/approved`) 게이트를 파일럿 전에 `approved_only` 로 올린다.

## 5. Non-Goals (Out of Scope, 1차)

- 알레르기내과 외 진료과, SPT(피부단자검사) 결과 자동 수신(2차).
- HIS 로의 결과 **역전송**(판정·FHIR 번들 기록) — 설계만 하고 구현은 2차.
- 환자 앱(네이티브) 개발 — 모바일 웹으로 충분.
- 외부 클라우드 배포(Render 등) — 병원 로컬 서버가 1차 대상. 기존 데모 배포는 유지.
- 알림톡 대행사 신규 계약·카카오 비즈니스 채널 신규 개설(병원 기존 계약 사용).
- 다국어 알림톡(한국어만; 설문·리포트의 영/중은 기존 기능 유지).

## 6. Design Considerations

- 환자 화면은 현행 두 UI(`/` 퀘스트, `/classic/`) 중 **클래식 UI 를 모바일 기본**으로 하고, 퀘스트 UI 는 선택 링크로 둔다(알림톡 인앱 브라우저에서 애니메이션 부담 최소화).
- 알림톡 템플릿은 버튼형(웹링크 버튼 1~2개) 으로, 본문에는 병원명·검사명·검사일·소요시간·개인정보 고지만 넣는다.
- QR 은 챗봇 URL 하나로 통일하고 PDF 마지막 장에도 인쇄한다.

## 7. Technical Considerations

- **기존 자산 재사용**: `models/schemas.py`(OCRResult·AllergenResult), `services/relevance_service.py`·`questionnaire_service.py`·`report_service.py`·`report_pdf.py`·`cardnews_*.py`·`fhir_service.py`·`result_chat_service.py`·`store_service.py`(SQLite 세션)·`email_service.py`(발송 한도 패턴을 알림톡에 재사용)·`admin_api.py`.
- **신규 모듈(안)**: `services/his_ingest/`(hl7v2.py · fhir_pull.py · db_batch.py · normalize.py), `services/token_service.py`, `services/alimtalk_service.py`, `services/job_queue.py` + `worker.py`, `services/qr_service.py`, `web/m/`(모바일 설문 진입·본인확인).
- **HL7 v2 파싱 라이브러리**: `hl7apy` 또는 `python-hl7`; MLLP 수신기는 `asyncio` 서버. FHIR 는 `fhir.resources`(이미 FHIR 생성에 사용 중인지 확인).
- **큐**: 운영 단순화를 위해 1차는 SQLite 기반 큐(현 `store_service` 와 같은 DB) + 단일 워커, 부하 시 Redis/RQ 로 교체 가능한 인터페이스.
- **보안**: 내부망 서버 ↔ DMZ 역프록시(TLS 종단) ↔ 인터넷. 외부 inbound 는 토큰 URL 경로(`/m/*`, `/api/sessions/*`)만 허용. 알림톡 대행사 outbound 만 방화벽 허용. 저장 데이터 암호화(디스크 또는 필드 수준), 관리자 2FA.
- **로컬 LLM 실측치(연구실 DGX Spark, 2026-10)**: nginx 1MB 요청 한도, OCR 장당 4~5분, 폭주 시 서버 중단 경험 → 병원 서버에서는 요청 크기 제한 해제·타임아웃·워커 1~2개·벽시계 상한을 처음부터 설정.
- **HIS 수신 세 안의 비교**

| 안 | 장점 | 단점 | 의료정보팀 작업 | 우리 팀 작업 |
|---|---|---|---|---|
| A-1 HL7 v2 | 국내 HIS/LIS 표준 경로, 실시간, 결과 수정 메시지 처리 가능 | 인터페이스 엔진 라우팅 추가·테스트 필요 | 라우팅 규칙·메시지 샘플·테스트 환경 | MLLP 수신기·파서·ACK |
| A-2 FHIR R4 | 기존 FHIR 코드와 정합, 구조 명확 | HIS 가 FHIR 서버를 제공해야 함(국내 드묾) | FHIR 엔드포인트·인증·범위 | pull/Subscription 클라이언트 |
| A-3 DB 뷰/배치 | 가장 빠르게 시작, 인터페이스 개발 없음 | 지연(배치 주기), 결과 수정 추적 어려움, DB 계정 보안 심의 | 읽기 전용 뷰·계정·스키마 문서 | 폴러·변환 |

권장: **A-3 으로 2주 내 데이터 검증을 시작하고 A-1 로 전환**(병행 운영 뒤 A-3 종료). A-2 는 HIS 가 FHIR 를 제공할 때만.

## 9. Open Questions (의료정보팀 킥오프에서 확인)

1. 인터페이스 엔진 종류와 HL7 v2 버전(2.3/2.5), 알레르기 검사의 OBX 코드 체계(원내 코드·LOINC 여부), class/수치 표현 방식.
2. HIS 가 FHIR R4 엔드포인트를 제공하는가? 제공한다면 인증 방식과 허용 범위.
3. DB 읽기 전용 뷰 제공 가능 여부와 보안 심의 소요 기간.
4. 알림톡 대행사명·API 방식·템플릿 등록 절차와 소요(보통 2~5 영업일), 발신 프로필(병원 채널) 사용 조건.
5. 환자 연락처·수신 동의 플래그의 소재와 조회 권한. 알림톡 발송에 별도 동의가 필요한가(개인정보 담당자 판단).
6. 로컬 서버·GPU 사양(모델·VRAM·디스크), OS, 컨테이너 사용 가능 여부, 외부 도메인·TLS 인증서 발급 주체.
7. DMZ 역프록시 구성과 inbound 허용 정책, 알림톡 대행사 outbound 허용.
8. 결과 수정(corrected)·취소 메시지 빈도와 처리 기대치.
9. 파일럿 대상 환자 범위(신환만? 재검 포함?), 소아 환자(보호자 연락처) 처리.
10. 의료진 조회 화면을 HIS 안에 링크(SSO) 로 둘 수 있는가, 아니면 별도 로그인인가.
11. 연구(IRB) 로 갈지 QI 사업으로 갈지 — 데이터 2차 활용 범위에 영향.
